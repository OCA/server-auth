Lets members of an organization log in as one shared Odoo user
(``admin`` by default) with their own account at an OpenID Connect
provider (e.g. Microsoft Entra ID), instead of sharing its password.

- No button is added to the login page: the flow starts by opening
  ``/auth_admin_sso/login`` manually.
- ``/web/login`` keeps working as usual (e.g. to log in as a portal
  user).
- No configuration is stored in the database: everything comes from
  environment variables or the Odoo configuration file.
- No client secret is needed: the flow uses the authorization code flow
  with PKCE, as a public client.
- Access is granted per instance through a role given by the provider.

Configuration
=============

Idp-side
--------

Provider requirements
~~~~~~~~~~~~~~~~~~~~~

The OpenID Connect provider must:

+-------------------+--------------------------------------------------+
| Feature           | Description                                      |
+===================+==================================================+
| **Discovery**     | Publish                                          |
|                   | ``<issuer>/.well-known/openid-configuration``    |
+-------------------+--------------------------------------------------+
| **Public client** | Authorization code flow with PKCE, without       |
|                   | client secret                                    |
+-------------------+--------------------------------------------------+
| **Redirect URI**  | Accept                                           |
|                   | ``https://<instance>/auth_admin_sso/callback``,  |
|                   | one per instance                                 |
+-------------------+--------------------------------------------------+
| **Signature**     | Sign the ID token with ``RS256``                 |
+-------------------+--------------------------------------------------+
| **Roles claim**   | Put the user's roles in an ID token claim        |
|                   | (``roles`` by default), as a list or a single    |
|                   | string                                           |
+-------------------+--------------------------------------------------+

Known providers (only automated tests so far, no live test):

+----------------------------+------------+-----------------------------------------------+
| Provider                   | Compatible | Note                                          |
+============================+============+===============================================+
| **Microsoft Entra ID**     | Yes        | Roles in the ``roles`` claim                  |
+----------------------------+------------+-----------------------------------------------+
| **Keycloak**               | Yes        | Public client; add a role mapper to the ID    |
|                            |            | token, set ``AUTH_ADMIN_SSO_ROLES_CLAIM``     |
+----------------------------+------------+-----------------------------------------------+
| **Okta**                   | Yes        | Native app with PKCE; add a groups claim, set |
|                            |            | ``AUTH_ADMIN_SSO_ROLES_CLAIM``                |
+----------------------------+------------+-----------------------------------------------+
| **Auth0**                  | Yes        | Native app with PKCE; add roles with an       |
|                            |            | Action, set ``AUTH_ADMIN_SSO_ROLES_CLAIM``    |
+----------------------------+------------+-----------------------------------------------+
| **AWS Cognito**            | Yes        | App client without secret; set                |
|                            |            | ``AUTH_ADMIN_SSO_ROLES_CLAIM=cognito:groups`` |
+----------------------------+------------+-----------------------------------------------+
| **GitLab**                 | Yes        | Non-confidential application; roles are       |
|                            |            | GitLab groups, set                            |
|                            |            | ``AUTH_ADMIN_SSO_ROLES_CLAIM=groups_direct``  |
+----------------------------+------------+-----------------------------------------------+
| **Google Workspace**       | No         | Requires a client secret, sends no roles      |
+----------------------------+------------+-----------------------------------------------+
| **GitHub**                 | No         | Not OpenID Connect                            |
+----------------------------+------------+-----------------------------------------------+

Example IdP setup
~~~~~~~~~~~~~~~~~

Example with Microsoft Entra ID. One app can serve all instances, but
one app per customer is recommended.

1. Create an ``App Registration``.
2. In ``Authentication``, add the platform
   ``Mobile and desktop applications`` and add one redirect URI per
   instance: ``https://<instance>/auth_admin_sso/callback``.
3. In ``Authentication``, enable ``Allow public client flows``.
4. In ``App roles``, create one role per instance (e.g.
   ``odoo-customer-a``).
5. In ``Enterprise applications`` > ``Users and groups``: assign that
   role to the users or groups allowed on that instance. ⇒ they log in
   as the default login of the instance.
6. You can enforce the username through the role
   ``odoo-customer-a.username.<username>``. It takes priority over
   ``odoo-customer-a``.

Odoo-side
---------

On each Odoo instance, set these environment variables (or the same
names, lowercase, in the ``[options]`` section of the configuration
file).

+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| Variable                                  | Default Value | Required      | Description                                            |
+===========================================+===============+===============+========================================================+
| ``AUTH_ADMIN_SSO_PROVIDER``               | ``oidc``      | No            | Provider implementation: ``oidc``, or one added by     |
|                                           |               |               | another add-on                                         |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_ISSUER``                 |               | With ``oidc`` | Issuer URL, e.g.                                       |
|                                           |               |               | ``https://login.microsoftonline.com/<tenant id>/v2.0`` |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_CLIENT_ID``              |               | With ``oidc`` | Client id (Entra ID: app registration id)              |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_REQUIRED_ROLE``          |               | Yes           | Role of the instance, e.g. ``odoo-customer-a``; prefix |
|                                           |               |               | of the username roles                                  |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_ROLES_CLAIM``            | ``roles``     | No            | ID token claim holding the roles                       |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_DEFAULT_LOGIN``          | ``admin``     | No            | Odoo login granted by the role of the instance         |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_REDIRECT_LOGIN``         | disabled      | No            | Enabled (``1``, ``true``, ``yes``) or disabled (any    |
|                                           |               |               | other value): ``/web/login`` with the default login    |
|                                           |               |               | and the redirect keyword goes to the SSO               |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_REDIRECT_KEYWORD``       | ``sso``       | No            | Password triggering that redirect; not a secret,       |
|                                           |               |               | compared in plain text                                 |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+
| ``AUTH_ADMIN_SSO_CASE_INSENSITIVE_LOGIN`` | disabled      | No            | Enabled (``1``, ``true``, ``yes``) or disabled (any    |
|                                           |               |               | other value): ignore case when comparing the login for |
|                                           |               |               | that redirect                                          |
+-------------------------------------------+---------------+---------------+--------------------------------------------------------+

``/auth_admin_sso/login`` answers 404 while
``AUTH_ADMIN_SSO_REQUIRED_ROLE`` is missing, or, with the ``oidc``
provider, ``AUTH_ADMIN_SSO_ISSUER`` or ``AUTH_ADMIN_SSO_CLIENT_ID``. An
unknown provider answers 500.

Design
~~~~~~

Why the instance sets the default login
^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^

Why the default Odoo login comes from the instance configuration and not
from the provider:

- Granting access and configuring the instance are done by different
  people.

  - The person granting access (e.g. a team manager) only assigns the
    role of the instance (e.g. ``odoo-customer-a``), without knowing
    which Odoo user it maps to.
  - The person deploying the instance knows its Odoo users (e.g. the
    admin login may not be ``admin``).

- When a specific Odoo login must be granted, the role
  ``odoo-customer-a.username.<username>`` does it without changing the
  instance configuration.

Server-wide without installation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Load the module without installing it by adding it to the server wide
modules: ``--load=base,web,auth_admin_sso`` (or ``server_wide_modules``
in the configuration file). Installing it in the database works too.

Usage
=====

1. Open ``https://<instance>/auth_admin_sso/login``, ⇒ this redirects
   you to your IdP
2. log in with your provider account (e.g. Entra ID) ⇒ You get
   redirected to Odoo and logged as

   - ``<username>``, if you have the role
     ``<required role>.username.<username>``;
   - else the default login (``admin`` unless configured), if you have
     the role ``<required role>``;
   - else the login is refused.

Access from login form
----------------------

With ``AUTH_ADMIN_SSO_REDIRECT_LOGIN`` enabled, the login form can start
the SSO:

1. Login: the default login (``admin`` unless configured).
2. Password: the redirect keyword (``sso`` unless configured). It is not
   a secret: it only redirects to the provider login, which still checks
   your account and role.

Any other login or password gets the usual Odoo password check.

MFA/2FA
-------

The Odoo two-factor authentication of that user is not asked: the
provider is responsible for it. Each login is logged with the email from
the provider.

Login Failure
-------------

When the login fails, the page only shows a reference (a random UUID),
never the cause. Give that reference to an administrator: the server log
has a warning with the same reference and the exact cause.

Development
===========

Another add-on adds a provider by inheriting the ``AdminSSO`` controller
and overriding its ``_auth_admin_sso_*`` methods (also as a server wide
module, since there is no model):

.. code:: python

   from odoo.addons.auth_admin_sso.controllers.main import AdminSSO


   class MyAdminSSO(AdminSSO):
       def _auth_admin_sso_authorization_url(self, settings, redirect_uri, state, nonce,
                                  challenge):
           if settings["provider"] != "my_provider":
               return super()._auth_admin_sso_authorization_url(
                   settings, redirect_uri, state, nonce, challenge)
           return "https://my-provider.example.com/authorize?..."

       # Same for _auth_admin_sso_fetch_claims, _auth_admin_sso_check_nonce, _auth_admin_sso_get_roles and
       # _auth_admin_sso_get_identity.

Then set ``AUTH_ADMIN_SSO_PROVIDER=my_provider``. Every step of the flow
is an overridable ``_auth_admin_sso_*`` method of ``AdminSSO`` (e.g.
``_auth_admin_sso_select_login``, ``_auth_admin_sso_login_as``). The
settings methods (``_auth_admin_sso_get_settings``, ...) come from
``AdminSSOSettingsMixin``, shared with the ``/web/login`` override
``AdminSSOHome``: override them in a subclass of both controllers.
